# Auth Service — Техническое задание

> **Статус:** 🟢 Почти готово  
> **Назначение:** Аутентификация, OAuth, сессии, верификация

---

## 1. Бизнес-функции

- Регистрация (email + password + username)
- Логин (email/password)
- Логаут (очистка сессии)
- Ротация refresh token
- Верификация email (письмо с токеном)
- Повторная отправка верификации
- Восстановление пароля (forgot + reset)
- OAuth: GitHub, Google
- Управление сессиями: просмотр, отзыв одной, отзыв всех
- Блокировка аккаунта при 5+ неудачных попытках логина

## 2. Ключевые бизнес-сценарии

### Регистрация и вход
```
1. Пользователь вводит email, password, username
2. Система создаёт учётную запись (credentials)
3. Отправляется письмо с верификацией
4. При первом входе — проверка почты
5. После верификации — полный доступ
```

### OAuth
```
1. Выбор провайдера (GitHub / Google)
2. Редирект на страницу провайдера
3. Подтверждение доступа пользователем
4. Callback → создание/привязка учётной записи
5. Автоматический вход
```

### Восстановление пароля
```
1. Запрос сброса по email
2. Письмо с одноразовой ссылкой (1 час)
3. Установка нового пароля
4. Автоматическая очистка всех сессий
```

## 3. Важные нюансы

- **Токены** — Access + Refresh JWT в HttpOnly cookies. Refresh токен хранится в БД как SHA-256 хэш.
- **Защита от replay attack** — если использован отозванный refresh token → все сессии пользователя принудительно завершаются.
- **Instant revoke** — отзыв сессии → удаление из Redis → следующий запрос получает 401.
- **Rate limiting** — 5 попыток входа / 15 минут. После превышения — блокировка на 15 минут.
- **Cooldown писем** — повторная отправка верификации / сброса пароля — не чаще 1 раза в 60 секунд.
- **Cессии хранят** — метаданные устройства (OS, браузер, IP, страна) для отображения в списке сессий.
- **Очистка** — неподтверждённые аккаунты старше 24ч удаляются автоматически (каждый час).

## 4. Acceptance Criteria / Expected Behavior

### TC-AUTH-1: Регистрация нового пользователя

**Preconditions:**
- Пользователь не авторизован
- email: `user@example.com` не зарегистрирован

**Flow:**
1. Пользователь открывает `/auth/register`
   → Видит форму: username, email, password, confirm password
2. Вводит username = `john`, email = `user@example.com`, password = `Pass123!@#`, confirm = `Pass123!@#`
3. Нажимает "Зарегистрироваться"
   → Кнопка становится disabled, отображается спиннер
4. Через 1-3 секунды:
   → Если успех: редирект на `/auth/check-email` с сообщением "Проверьте почту"
   → Если ошибка: подсветка поля + сообщение (например "Email уже используется")
5. На почту приходит письмо:
   → Тема: "Подтверждение email"
   → Содержит кнопку "Подтвердить email"
   → Срок действия: 24 часа

**Ошибки валидации:**
- **Username < 2 символов:** красная подсветка, "Минимум 2 символа"
- **Неверный формат email:** "Введите корректный email"
- **Password без цифры/спецсимвола/длины < 8:** "Пароль должен содержать..."
- **Confirm password не совпадает:** "Пароли не совпадают"
- **Email уже существует:** ошибка 409 "Email уже зарегистрирован"

### TC-AUTH-2: Верификация email

**Preconditions:**
- Пользователь только что зарегистрировался
- Находится на странице `/auth/check-email`

**Flow:**
1. Пользователь открывает письмо, нажимает "Подтвердить email"
   → Открывается страница `/auth/email-verified?token=...`
2. Если токен валиден:
   → Страница: "Email подтверждён!", кнопка "Перейти в чаты"
   → HttpOnly cookies установлены (автоматический вход)
3. Пользователь нажимает "Перейти в чаты"
   → Редирект на `/chats`

**Ошибки:**
- **Токен истёк (24ч+):** страница "Ссылка устарела", кнопка "Отправить повторно"
- **Токен невалидный:** "Ссылка некорректна"
- **Повторная верификация уже верифицированного:** "Email уже подтверждён"

---

### TC-AUTH-3: Логин

**Preconditions:**
- Пользователь зарегистрирован и верифицирован

**Flow:**
1. Пользователь открывает `/auth/login`
   → Форма: email, password, кнопка "Войти", ссылки "Забыли пароль" + OAuth кнопки
2. Вводит email = `user@example.com`, password = `Pass123!@#`
3. Нажимает "Войти"
   → Кнопка disabled + спиннер
4. Успех:
   → Редирект на `/chats`
   → HttpOnly cookies: access_token + refresh_token
5. Пользователь обновляет страницу
   → Остаётся в `/chats` (сессия восстановлена через cookie)

**Ошибки:**
- **Неверный email:** "Пользователь не найден"
- **Неверный пароль:** "Неверный пароль"
- **Email не подтверждён:** "Подтвердите email", кнопка "Отправить повторно"
- **Аккаунт заблокирован (5 неудачных попыток):** "Аккаунт заблокирован на 15 минут"
- **5 неудачных попыток подряд:** после 5й — сообщение о блокировке

---

### TC-AUTH-4: OAuth (GitHub / Google)

**Flow:**
1. Пользователь нажимает "Войти через GitHub" на странице логина
   → Редирект на GitHub: авторизация приложения
2. Пользователь подтверждает доступ
   → Callback на сервер
   → Если пользователь существует: логин (cookies установлены)
   → Если новый: создание аккаунта + профиля + логин
3. Редирект на `/chats`

**Edge cases:**
- **Email от OAuth совпадает с существующим:** связывание аккаунта
- **Ошибка провайдера:** редирект обратно на логин с ошибкой "Ошибка авторизации через {provider}"
- **Отмена на стороне провайдера:** возврат на логин

---

### TC-AUTH-5: Refresh token (прозрачный)

**Preconditions:**
- Пользователь авторизован, access_token скоро истечёт

**Flow:**
1. Пользователь работает в приложении
2. Приложение делает запрос к API → сервер возвращает 401
3. Клиент автоматически (без участия пользователя):
   → POST /api/auth/refresh (refresh_token из cookie)
   → Сервер проверяет refresh token, выдаёт новую пару
   → Исходный запрос повторяется с новым access_token
4. Пользователь ничего не замечает — запрос выполнен успешно

**Ошибка:**
- **Refresh token истёк:** редирект на `/auth/login`
- **Refresh token отозван (replay attack):** система отзывает все сессии пользователя — редирект на `/auth/login`

---

### TC-AUTH-6: Управление сессиями

**Preconditions:**
- Пользователь авторизован на 3 устройствах (Windows/Chrome, Mac/Safari, iOS)

**Flow:**
1. Пользователь открывает Настройки → Устройства
   → Список сессий: название устройства, браузер, ОС, IP, страна, время последней активности
   → Текущая сессия помечена "Это устройство"
2. Пользователь нажимает "Отозвать" на сессии Mac/Safari
   → Сессия исчезает из списка
   → Mac/Safari: при следующем запросе — 401, редирект на логин
3. Пользователь нажимает "Завершить все остальные сессии"
   → Все сессии, кроме текущей, отозваны
   → Другие устройства разлогинены принудительно

---

### TC-AUTH-7: Восстановление пароля

**Flow:**
1. Пользователь нажимает "Забыли пароль?" на странице логина
   → Поле для ввода email
2. Вводит email, нажимает "Отправить"
   → "Проверьте почту"
3. Приходит письмо с кнопкой "Сбросить пароль" (срок 1 час)
4. Пользователь переходит по ссылке → форма нового пароля
5. Вводит новый пароль дважды, сохраняет
   → Все сессии отозваны (кроме текущей, если пользователь авторизован)
   → Если не авторизован: редирект на `/auth/login` с сообщением "Пароль изменён"

**Ошибки:**
- **Email не зарегистрирован:** всё равно "Проверьте почту" (security through obscurity)
- **Токен истёк:** ссылка не работает, "Запросите сброс снова"
- **Повторный запрос <60s:** "Повторите через минуту"

---

### TC-AUTH-8: Блокировка аккаунта

**Preconditions:**
- Аккаунт существует, пользователь НЕ знает пароль

**Flow:**
1. Пользователь вводит неверный пароль 5 раз подряд
   → После 1-4: "Неверный пароль" (счётчик увеличивается)
   → После 5: "Аккаунт заблокирован на 15 минут"
2. Пользователь пытается войти сразу: "Аккаунт заблокирован ещё на 14 минут"
3. Через 15 минут: вход снова возможен
4. Если пользователь сбросит пароль через "Forgot password" — блокировка снимается
