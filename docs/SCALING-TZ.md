# ТЗ: доведение Polygon до хорошего состояния на одной машине

Дата: 2026-10-01. Статус: на ревью. Область: один сервер класса 12 CPU / 15 ГБ RAM,
все сервисы и инфра на нём. Вторая машина, шардирование, мульти-хост — вне скоупа.

## 1. Исходные данные (замерено 2026-10-01, стенд dev, троттлер снимался временно)

| Нагрузка | RPS / msg | p95 | Ошибки | Вывод |
|---|---|---|---|---|
| HTTP щадящий, 500 VU | ~100 RPS | 68мс | 0% | зелёный |
| HTTP paced 200 RPS | 200 | 52мс | 0% | зелёный |
| HTTP paced 280 RPS | 280 | 66мс | 0% | зелёный |
| HTTP без слипа, 120–800 VU | ~340–382 | 760мс–2.9с | 0% (103к запросов) | красный по latency, ошибок нет |
| WS запись, 100 сокетов | ~65 msg/с | ok | 100% `message:new` | зелёный |
| WS запись, 500 сокетов | ~132 msg/с | таймауты 5с | 90% `message:new` | деградация |
| WS запись, 1000 сокетов | ~165 msg/с | медиана 5с | 11% `message:new` | коллапс рассылки |
| Троттлер как есть | 100 req/мин на IP | — | 100% 429 сверх | стена для любого NAT |

Система не ломается (0% 5xx на 100к+ запросов), а тормозит. Память сокетов
~0.3–1МБ/штука на gateway. PG-коннекты пиком 27 — БД не узкое место.
Gateway — один Node-процесс на одном ядре (CPU 3–5% от машины в пик).

## 2. Целевые показатели (критерии приёмки всего ТЗ)

Замеряется существующим набором `infra/load` (k6 через docker) + дашборд
`polygon-backend-overview` (Prometheus `:9090`, Grafana `:3009`).
Деградация = p95 > 500мс ИЛИ ошибки > 1%.

- **Ц1.** HTTP смешанная нагрузка (чаты/сообщения/поиск 1:1:1:1): paced **1000 RPS**,
  p95 < 500мс, ошибок < 1%, прогон 5 минут.
- **Ц2.** WS запись (`message:send` → `message:new`): **1000 конкурентных писателей**,
  доставлено ≥ 99% за ≤ 2с каждое, прогон 3 минуты.
- **Ц3.** WS онлайн в простое: **3000 сокетов**, коннект p95 < 500мс, память gateway
  ≤ 6 ГБ, прогон 5 минут.
- **Ц4.** Офис за одним NAT (50 юзеров с одного IP, человеческий темп): **0% 429**.
- **Ц5.** Память gateway после прогона возвращается к baseline ±20% за 5 минут
  (нет утечек сокетов/подписок).

## 3. Работы

### Блок 1. Троттлер per-user (обязательно первым)

**Зачем:** сейчас 100 req/мин на IP — один офис за NAT кладёт всех (Ц4).
Файлы: `apps/backend/gateway/src/app/gateway.module.ts`,
кастомный guard поверх `@nestjs/throttler` (ключ по `sub` из JWT,
fallback на IP для неавторизованных), конфиг лимитов через env
(`libs/backend/core/src/config/env.schema.ts` + `.env*` + compose при нужде).

**Требования:**
- Лимит по пользователю: 300 req/мин; по IP для анонимов: 100 req/мин (как сейчас).
- Превышение отвечает 429 с `Retry-After`; метрика счётчика 429 в Prometheus.
- Прод-лимит меняется только этим блоком, временные отключения для замеров запрещены.

**Готовность:** Ц4 зелёный; k6-проверка 300 req с одного IP одним юзером даёт 429,
тремя юзерами — 0% 429.

### Блок 2. Cluster-режим gateway

**Зачем:** главный выигрыш — сейчас 1 ядро из 12, упёрлись в event loop
(потолок ~350 RPS на процесс).
Файлы: entry gateway (`apps/backend/gateway`), конфиг запуска
(`docker/demo`, локальный `dev:all`), nginx `docker/demo/nginx` (sticky sessions
по IP либо по куке).

**Требования:**
- Число воркеров = `CPU - резерв` (на этой машине: 6 воркеров gateway,
  остальное — сервисы/инфра), задаётся env `GATEWAY_WORKERS` с дефолтом.
- Сокеты: либо sticky sessions в nginx, либо `@socket.io/redis-adapter`
  на существующем Redis (предпочтительно адаптер — переживает рестарт воркера).
- Метрики `/api/metrics` агрегируются со всех воркеров (prom-client cluster
  или один агрегатор), дашборд не должен разъехаться.
- Graceful shutdown воркеров (дослужить сокеты/закрыть RMQ-каналы).

**Готовность:** Ц1 зелёный; `ws_connecting` p95 < 100мс при Ц2.

### Блок 3. Путь отправки WS-сообщения

**Зачем:** на каждое сообщение два похода в RMQ (`CHECK_MEMBERSHIP` + `SEND_MESSAGE`)
плюс инвалидация кеша; рассылка сыплется первой (11% на 1000).
Файлы: `apps/backend/gateway/src/gateways/chat.socket-gateway.ts`,
`GatewayChatCacheService`, chat-service (`libs/backend/chat`).

**Требования:**
- Членство в чате кешировать в Redis (`membership:{chatId}:{userId}`, TTL 30–60с,
  инвалидация при выходе/кике); RMQ `CHECK_MEMBERSHIP` — только при промахе кеша.
- Антиспам-лимит `message:send`: 30 msg/мин на пользователя (429-ошибка сокета
  `RATE_LIMITED`, в логах только флаги), настраивается через env.
- Join-ack: сервер подтверждает `chat:joined` после фактического `socket.join`;
  клиент (и k6-сценарий) шлёт первое сообщение только после ack — закрывает
  известную гонку «отправил сразу после join, своё сообщение не получил»
  (сейчас в `ws-load.js` костыль-задержка 500мс — убрать после фикса).
- Broadcast оставить `server.to(chat:{id}).emit`, замерить; если Ц2 не берётся —
  вынести fan-out в отдельный воркер-тред gateway (решение фиксируется замером).

**Готовность:** Ц2 зелёный; `ws-load.js` без задержки 500мс; RMQ-трафик на отправку
−40% минимум (считать по метрикам очередей `chat_queue`).

### Блок 4. Конкуренция потребителей RMQ

**Зачем:** после блоков 2–3 следующим упрётся обработка очередей.
Файлы: entry каждого сервиса (`apps/backend/*-service`), конфиги RMQ-клиентов
в gateway (`gateway.module.ts`).

**Требования:**
- Явные `prefetchCount` и число консюмеров chat/auth/user-сервисов через env
  (стартовые значения: prefetch 50, консюмеры = половина воркеров gateway).
- Длина очередей (`rabbitmq_queue_messages`) в Grafana с алертом > 1000.
- Рестарт консюмера не теряет сообщения (durable очереди уже есть — проверить ack).

**Готовность:** при Ц1 длина `chat_queue` p95 < 200 сообщений.

### Блок 5. Базы данных: пулы и индексы

**Зачем:** сейчас запас есть (пик 27 коннектов), но при росте в 3–5 раз упрёмся.
Файлы: `PrismaService` каждого `libs/backend/*`, `prisma.config.ts` (одинаковые,
меняется только `*_DATABASE_URL`), `infra/db/init` при нужде.

**Требования:**
- Явные лимиты пулов Prisma через env (`connection_limit` на сервис:
  chat 20, остальные 10), итоговая сумма < `max_connections` Postgres с запасом 30%.
- Аудит индексов под горячие запросы: сообщения чата (chatId, createdAt/ид),
  членство (chatId+userId), сессии (хеш токена, userId). `EXPLAIN` до/после в отчёте.
- PgBouncer (transaction mode) — опционально, только если пулов не хватит
  (решение замером, не заранее).

**Готовность:** при Ц1+Ц2 активных коннектов < 70% лимита; медленных запросов
(>200мс) < 0.1% по `pg_stat_statements` или логам.

### Блок 6. Auth-сессии и refresh-шторм

**Зачем:** access живёт 15 мин — при тысячах онлайна постоянный фон refresh-трафика
в Redis + auth-service.
Файлы: auth-service (`libs/backend/auth`), `CoreTokenModule`/`CoreRedisModule`
(`libs/backend/core`), env `JWT_*`.

**Требования:**
- `JWT_ACCESS_TOKEN_EXPIRES` поднять до 3600 (env, без кода), refresh оставить 7 дней.
- Ротация и защита от reuse — как есть, не ослаблять.
- Лимит логинов с одного email оставить (5 попыток), проверить что легитимный
  refresh-шторм после рестарта gateway не упирается в него.

**Готовность:** при Ц3 фон `/auth/refresh` < 5% всего RPS gateway.

### Блок 7. Наблюдаемость и алерты

**Зачем:** стек уже стоит (Prometheus/Grafana/Loki/Tempo), нет порогов.
Файлы: `infra/observability/prometheus/rules`, дашборд `polygon-backend-overview`.

**Требования (алерты):**
- p95 latency gateway > 500мс дольше 3 минут.
- Длина любой `*_queue` > 1000 дольше 2 минут.
- 429 rate > 5% дольше 2 минут (после блока 1 — значит атака или баг клиента).
- RSS gateway > 80% лимита контейнера/машины.
- PG-коннекты > 70% `max_connections`.
- Каждый алерт: куда приходит + кто реагирует (записать в README наблюдаемости).

**Готовность:** правила закоммичены, тестовый прогон каждого алерта (форсированная
нагрузка) показывает срабатывание и затухание.

### Блок 8. Нагрузочная приёмка (регресс-гейт)

**Зачем:** зафиксировать Ц1–Ц5 как повторяемую процедуру, иначе деградация вернётся.
Файлы: `infra/load/*` (дополнить), `infra/load/README.md`.

**Требования:**
- Сценарии: paced HTTP 1000 RPS / 5 мин; WS 1000 писателей / 3 мин;
  WS 3000 idle / 5 мин; NAT-тест 50 юзеров с одного IP.
- Сид масштабировать: `SEED_N` до 1000+ (сейчас 50; регистрация упирается
  в SMTP/верификацию — сид через прямую верификацию в БД оставить как
  test-only процедуру с префиксом `load_`).
- Каждый блок 1–6 сдаётся прогоном своего сценария до/после с таблицей в PR.
- Финальный отчёт: таблица Ц1–Ц5 факт vs цель.

**Готовность:** `bash infra/load/run.sh <scenario>` из чистой машины даёт
воспроизводимые Ц1–Ц5; README описывает процедуру.

## 4. Порядок внедрения

1. Блок 1 (троттлер) — разблокирует честные замеры и NAT-кейс.
2. Блок 3 (путь отправки) — самая дорогая операция, независим от кластера.
3. Блок 2 (кластер) — главный прирост, после него перемерить всё.
4. Блоки 4–5 (RMQ, БД) — по факту узких мест после 1–3, лишнее не делать.
5. Блок 6 (сессии) — параллельно, дешево.
6. Блок 7 (алерты) — после стабилизации порогов.
7. Блок 8 (приёмка) — непрерывно, финал после всех.

## 5. Общие ограничения (из AGENTS.md, обязательны)

- NPM only, `package-lock.json` — источник правды.
- Контракты первыми: новые шейпы — zod в `libs/common`, бэкенд оборачивает
  (`createZodDto`), фронт расширяет; маршруты только из `API_ROUTES`.
- Транспорт: HTTP-контроллеры только в Gateway; либы — `@MessagePattern`/
  `@EventPattern`; новые паттерны — в `libs/backend/core/src/constants/queues/*`.
- Guards порядок: Throttler → Session/Jwt → ActiveAccount → Roles.
- Ошибки: сервисы кидают RPC `{ message, status }`, gateway маппит в HttpException.
- Без секретов в логах (только флаги присутствия + `eventType` `*_requested →
  *_started → *_done`).
- Тесты: спеки в `__tests__/` рядом с кодом; новое поведение без спеки — на доработку.
- Проверка после изменений: `affected --target=test` из корня + `format:check`.

## 6. Вне скоупа

Второй сервер, Redis adapter между хостами, шардирование Postgres/Meili,
мультирегион, E2E через браузер, хаос-тесты брокера/БД, CI-джоба нагрузки.

## 7. Риски

- Кластер + сокеты: sticky sessions vs adapter — выбрать замером на блоке 2,
  adapter может съесть часть выигрыша на broadcast.
- Одна машина: Postgres/RMQ/Redis дерутся за те же ядра — потолок Ц1 может
  упереться в железо раньше 1000 RPS; тогда фиксируем факт и режем скоуп
  (уменьшаем Ц1 с обоснованием замером, а не додумыванием).
- Dev-сборка vs prod: все замеры финальной приёмки — на prod-билде
  (`docker/demo` или собранный dist), dev-serve даёт −10–20%.
